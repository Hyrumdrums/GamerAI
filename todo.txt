DONE 2026-08-21: search-toggle bug ("cool"/"hi"/"error?" came back as fully
  empty assistant replies). Root-caused via code read, not live repro:
  - The search checkbox auto-unchecking after "cool" was NOT a bug — it's
    an existing by-design feature (streamingEngine.js: res.search_was_skipped
    auto-unchecks the box when the rewrite classifier decides a follow-up
    doesn't need search, e.g. "That's cool!" after a news thread). The
    Sources shown FOR "cool" itself were the small 3B routing classifier
    imperfectly judging a short ack as needing a definition lookup
    (Wikipedia/Merriam-Webster/Cambridge hits) -- a model-accuracy edge
    case in _build_search_query_meta_prompt, not a wiring bug. Left alone;
    could tighten the meta-prompt's short-ack examples later if it recurs.

    Ollama and only raises on an HTTP/transport failure. If Ollama's GPU
    inference dies mid-request (driver timeout/reset, OOM, crash — the
    GPU driver hiccup, unrelated to the sd.exe crash below which turned
    out NOT to be driver-related) it can return a clean
    HTTP 200 stream that goes straight to done:true with zero content
    tokens. process_one then reported that as status="complete" with
    text="", which the client renders as a bare "(empty)" bubble with no
    error styling and no retry button -- a silent, unactionable failure.
    Fixed: process_one now raises when result["text"] comes back blank,
    which routes through the existing except-Exception handler and reports
    status="error" instead — client shows "Generation failed." + a retry
    button, and the agent log gets a proper log.exception line. Applies to
    chat, search, and smart-mode jobs (same code path). Shipped in v1.3.6.

DONE 2026-08-21: image-gen crash on the GPU VPS test machine, sd.exe rc=
  3221226505 (STATUS_STACK_BUFFER_OVERRUN) loading dreamshaperXL-lightning
  .gguf. Root-caused with direct machine access (Remote Control session on
  the VPS) instead of guessing from a pasted log:
  - NOT a driver/VRAM issue. Windows System event log is completely silent
    in the crash window -- no TDR/driver-reset event fired. The "AMD
    Software" driver-timeout popup the user saw was coincidental.
  - Real cause, confirmed via WER (Event ID 1000/1001): sd.exe hit
    exception 0xC0000409 in ucrtbase.dll -- the CRT's /GS stack-cookie
    check killing the process because the GGUF loader corrupted its own
    stack while tallying per-tensor weight dtypes at model-load time
    (crashed before any generation/GPU work started). Looks like a fixed-
    size stack array overflowing on a model with more distinct quant types
    than expected -- dreamshaperXL-lightning's GGUF mixes f16 + q4_K.
  - This is a bug in the upstream stable-diffusion.cpp release binary
    (sd.exe is pulled prebuilt per infra/setup-image-mirror.sh, pinned to
    master-637-ef92a00 -- not built from source here, so not patchable
    directly), and dreamshaperXL-lightning is the one hardcoded default
    image model every Windows agent bootstraps -- not a one-VPS quirk.
  - Fixed (scoped, per go-ahead to "leave it for now" beyond this): agent.py
    now catches this specific rc and raises a clear message ("stack buffer
    overrun in the GGUF loader -- a known stable-diffusion.cpp bug ...
    not a driver or VRAM problem") instead of a raw rc + truncated stdout
    snippet. Revisit the model/binary swap only if this starts recurring
    more -- options on the table if so: pin a newer sd.exe release, swap
    to a uniformly-quantized (non-mixed-dtype) model variant, or file
    upstream with leejet/stable-diffusion.cpp.

DONE 2026-08-21: /register 401 token-mismatch mystery (state.json's token
  never matching the coordinator DB) recurred a second time on the same GPU
  VPS during a clean re-install flight test. Root-caused with direct machine
  access (a Claude session running on the VPS via Remote Control): the
  installer's postinstall "Launch now" checkbox + plain Start Menu/Desktop
  icons launch agent.exe with no --tray flag, and single-instance protection
  (_claim_single_instance) only ran for --tray launches -- so a plain console
  launch had zero protection against a second agent.exe process existing at
  the same time, and the two would silently clobber each other's state.json
  writes (including a just-issued signup token) with no coordination at all.
  Fixed: single-instance claiming now runs for any long-running launch, not
  just tray mode (still exempts --once/--status). Shipped in v1.3.7.


DONE 2026-08-21: "windows 11 doesn't hide in the tray like on pre-11".
  Root cause: Win11 defaults to Windows Terminal as the console host, and
  GetConsoleWindow() returns conhost's invisible ConPTY window in that
  case, not the visible WT tab -- so ShowWindow(SW_HIDE) hides a window
  nobody sees. Pre-11 (and Win11 with legacy console host set as default)
  works fine because GetConsoleWindow() there IS the visible window. No
  clean in-app fix exists (Win32 doesn't expose "which WT window is
  mine," and guessing risks hiding an unrelated terminal window of the
  user's) -- per owner's call, documented as a known limitation +
  workaround (switch default terminal app to Windows Console Host) in
  windows-agent/README_addendum.md instead of shipping a heuristic fix.
  Revisit with a real fix (consoleless CREATE_NO_WINDOW relaunch, trading
  away "Show console") if this keeps coming up.

  - RESEND_API_KEY / EMAIL_FROM added to .env (local) and .env.prod (VPS,
